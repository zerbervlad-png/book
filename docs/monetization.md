# Финансовая модель MVP — решение

## Выбранная модель: Вариант A — комиссия с каждой сделки

**Механика (реализована):**

| Параметр | Значение |
|---|---|
| Кто устанавливает цену места | Продавец (пользователь), при листинге |
| Комиссия по умолчанию | 5 % (`AM_PLATFORM_FEE`, `config.py`) |
| Override на уровень ресурса | `Resource.fee_percent` (организатор/платформа) |
| Из чьей суммы удерживается | **Из суммы продавца** |
| Что платит покупатель | Ровно цену места (`buyer_total = price`) |
| Что получает продавец | `price − fee_amount` |

Пример: цена 1 000 ₽, комиссия 5 % → покупатель платит 1 000 ₽,
сервис удерживает 50 ₽, продавец получает 950 ₽.

**Почему комиссия удерживается из суммы продавца, а не начисляется сверху:**
покупатель видит на карточке финальную цену без скрытых надбавок —
это упрощает UX и снижает споры «почему я плачу больше, чем написано».

**Где реализовано:**
- `engines/payment.py` — `compute_fee`, escrow-ledger (authorize → capture → refund);
- `engines/transfer.py` — `quote_listing` (превью цены/комиссии для покупателя);
- `api/transfers.py` — `GET /transfers/listings/{id}/quote`;
- `api/marketplace.py` — котировка включена в `/marketplace/listings`.

## Почему не Вариант B (подписка) для MVP

Подписка имеет смысл только при подтверждённом пуле **регулярных** продавцов.
На старте таких данных нет: большинство пользователей совершит 0–2 передачи.
Требовать подписку до формирования привычки — убить транзакционный оборот.

**Что заложено на будущее (без переделки):**
- комиссия уже параметризована (`fee_percent` на ресурс + дефолт платформы);
- подписка реализуется как «скидка/обнуление `fee_percent` для пользователя с
  активным тарифом» — точка применения одна: `compute_fee`;
- для этого достаточно добавить таблицу `user_subscriptions` и проверку тарифа
  в `compute_fee` — конвейер transfer/payment не меняется.

## Почему не Вариант C (нулевая модель) для MVP

- Без денег внутри приложения невозможен **escrow** → нет защиты покупателя
  («заплатил вне приложения — место не получили» становится нерешаемым спором).
- История сделок без расчётов не даёт разрешения конфликтов: спорные ситуации
  (ТЗ п.2) решаются только при финансовых следах операций.
- UX: расчёт внутри приложения — это и есть ценность посредника-маркетплейса.

## Подключение реального платёжного шлюза (PSP)

Заархитектировано заранее (раздел 71 старого ТЗ):
- `Payment.provider` — поле уже хранит имя провайдера (`ledger_escrow`);
- интерфейс шлюза = `authorize / capture / refund` в `engines/payment.py`;
- подключение ЮKassa/Stripe = реализация провайдера + проброс webhook,
  бизнес-логика Transfer не меняется;
- идемпотентность платежей (`idempotency_key`) уже защищает от двойных списаний.

Все статусы сделки (ТЗ п.4) покрыты конечным автоматом `TransferStatus`:
INITIATED → AWAITING_PAYMENT → VERIFYING → (AWAITING_BUYER_CLAIM) → COMPLETED,
плюс CANCELLED / REJECTED / EXPIRED; листинг — LISTED/закрыт; эскроу —
AUTHORIZED → CAPTURED / REFUNDED / FAILED.
